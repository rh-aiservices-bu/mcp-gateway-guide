= Phase 3: MCP Gateway Extension

Create the MCPGatewayExtension to connect the {mcp-gw} to your Gateway listener.

== Overview

The `MCPGatewayExtension` tells the MCP Gateway controller which Gateway listener to extend with MCP protocol support. This is the resource that *brings the data plane into existence*: until it exists there is no broker pod, and `MCPServerRegistration` resources stay `NotReady` because the controller does not know which Gateway to configure.

Applying it triggers the controller to create three things:

. The *broker-router Deployment* - the pod you did not see in xref:01-prerequisites.adoc[Phase 1], created in this extension's namespace
. An *EnvoyFilter* registering the router as an Envoy `ext_proc` filter on the target Gateway
. An *HTTPRoute* sending `/mcp` traffic on the target listener to the broker (when `httpRouteManagement: Enabled`)

Key fields used here:

* `targetRef` - the Gateway to extend, plus the listener via `sectionName` (must match a listener name on the Gateway; here `mcp`). It takes the listener's `name`, never its hostname or protocol. Name a listener that does not exist and the controller attaches nothing, creates no HTTPRoute, and the endpoint stays a 404. Check the names you actually have before applying:
+
[source,bash]
----
oc get gateway mcp-gateway -n "$GATEWAY_NAMESPACE" \
  -o jsonpath='{range .spec.listeners[*]}{.name}{"\t"}{.port}{"\t"}{.hostname}{"\n"}{end}'
----
+
[source]
----
mcp     8080    mcp.apps.cluster-example.com
mcps    8080    *.mcp.local
----
* `httpRouteManagement: Enabled` - let the controller own the HTTPRoute

The CRD has several other fields worth knowing about:

[cols="1,3", options="header"]
|===
| Field | Purpose

| `privateHost`
| Overrides the internal host the broker uses to hair-pin requests back through the Gateway. Defaults to `<gateway>-istio.<ns>.svc.cluster.local:<port>` - see <<privatehost>>.

| `publicHost`
| Overrides the public host derived from the listener hostname. Needed when the listener uses a wildcard and you need one specific host.

| `oauthProtectedResource`
| Serves OAuth metadata at `/.well-known/oauth-protected-resource`. Used in xref:07-authentication.adoc[Phase 7].

| `sessionStore`
| References a Secret with `CACHE_CONNECTION_STRING` for Redis-backed sessions. Without it, sessions live in the broker's memory and are lost on restart - relevant if you scale the broker beyond one replica.

| `backendPingIntervalSeconds`
| How often the broker health-checks upstream MCP servers.
|===

== Installation

Apply everything at once with Kustomize:

[source,bash]
----
oc apply -k manifests/03-mcp-gateway-extension/
----

That single command creates both resources described below. The individual manifests are documented here so you know what you just applied - you do not need to apply them separately.

=== The MCPGatewayExtension

`manifests/03-mcp-gateway-extension/mcpgatewayextension.yaml` binds the broker to the Gateway's `mcp` listener. Applying it is what causes the controller to create the broker Deployment.

=== The ReferenceGrant

`manifests/03-mcp-gateway-extension/referencegrant.yaml` authorises the extension to reference a Gateway in another namespace.

[cols="1,2", options="header"]
|===
| Your topology | Is the ReferenceGrant needed?

| Extension and Gateway in the same namespace (Track A default: both in `mcp-gateway`)
| No. It is applied anyway so the manifests work unchanged if you later split them.

| Extension and Gateway in *different* namespaces (Track B: Gateway in `openshift-ingress`)
| *Yes, mandatory.* Without it the extension never becomes Ready.
|===

IMPORTANT: A ReferenceGrant must live in the namespace of the resource being *referenced* - that is, the Gateway's namespace, not the extension's. On Track B that means creating it in `openshift-ingress`:

[source,bash]
----
oc apply -f - <<EOF
apiVersion: gateway.networking.k8s.io/v1beta1
kind: ReferenceGrant
metadata:
  name: allow-mcp-extension
  namespace: ${GATEWAY_NAMESPACE}
spec:
  from:
    - group: mcp.kuadrant.io
      kind: MCPGatewayExtension
      namespace: mcp-gateway
  to:
    - group: gateway.networking.k8s.io
      kind: Gateway
EOF
----

[#privatehost]
=== Setting privateHost on a non-istio GatewayClass

The extension's `privateHost` field tells the broker which address to dial when it re-enters the Gateway on the `mcps` listener. Left unset, it defaults to a name derived from the `istio` GatewayClass convention (`<gateway-name>-istio.<namespace>.svc.cluster.local`).

[WARNING]
====
On Track B that default points at a Service that *does not exist*. The failure is far nastier than a `NotReady` registration, because almost everything still works:

[cols="1,1,3", options="header"]
|===
| Check | Result | Why

| `oc get mcpgatewayextension`
| `Ready=True`
| The field is never resolved against the cluster, so a bogus host still validates

| `oc get mcpsr -A`
| `Ready=True`, correct `TOOLS` count
| Tool discovery does not use `privateHost` at all, so a bogus value never shows up here

| `initialize`
| works
| Handled by the broker itself

| `tools/list`
| works
| Served from the cached, aggregated tool list

| `tools/call`
| *fails*
| The only call that hair-pins back through the Gateway
|===

The error surfaces only on `tools/call`, and it names the Service that is missing:

[source]
----
failed to create session for mcp server: failed to create client: transport error:
failed to send request: Post "http://mcp-gateway-istio.mcp-gateway.svc.cluster.local:8080/mcp":
dial tcp: lookup mcp-gateway-istio.mcp-gateway.svc.cluster.local on 172.231.0.10:53: no such host
----

If you only ever run `initialize`, this install looks finished. Always run a real `tools/call` - see xref:05-verification.adoc[Phase 5].
====

Find the real Service and set the field:

[source,bash]
----
oc get svc -n "$GATEWAY_NAMESPACE" \
  -l gateway.networking.k8s.io/gateway-name=mcp-gateway

oc patch mcpgatewayextension mcp-extension -n mcp-gateway --type=merge -p "{
  \"spec\": {\"privateHost\": \"<service-name>.${GATEWAY_NAMESPACE}.svc.cluster.local:8080\"}
}"
----

Or without substituting the name by hand, reusing `GW_SVC` from xref:02-gateway-setup.adoc[Phase 2 Step 2]:

[source,bash]
----
oc patch mcpgatewayextension mcp-extension -n mcp-gateway --type=merge -p "{
  \"spec\": {\"privateHost\": \"${GW_SVC}.${GATEWAY_NAMESPACE}.svc.cluster.local:8080\"}
}"

oc rollout restart deployment/mcp-gateway -n mcp-gateway
----

The port must be the shared listener port from xref:02-gateway-setup.adoc[Phase 2] (`8080` here), and the broker needs a restart to pick the new value up.

== Verification

=== Wait for MCPGatewayExtension to be Ready

[source,bash]
----
oc wait mcpgatewayextension/mcp-extension -n mcp-gateway \
  --for=condition=Ready --timeout=60s
----

=== Confirm the Broker Appeared

This is the moment the data plane is created. The broker pod now exists:

[source,bash]
----
oc get pods -n mcp-gateway -l app.kubernetes.io/name=mcp-gateway
----

[source]
----
NAME                           READY   STATUS    RESTARTS   AGE
mcp-gateway-7d788b7b85-zpnnw   1/1     Running   0          17s
----

That single container is both the broker and the router. You can see the two ports:

[source,bash]
----
oc get deploy mcp-gateway -n mcp-gateway \
  -o jsonpath='{.spec.template.spec.containers[*].ports}'
----

[source]
----
[{"containerPort":8080,"name":"http"},{"containerPort":50051,"name":"grpc"},{"containerPort":8181,"name":"config"}]
----

`8080` serves the MCP protocol, `50051` serves gRPC for the Envoy `ext_proc` filter, `8181` serves config.

=== Check the HTTPRoute and EnvoyFilter were Created

With `httpRouteManagement: Enabled`, the controller creates an HTTPRoute for the broker, plus the EnvoyFilter that wires the router into Envoy:

[source,bash]
----
oc get httproutes -n mcp-gateway
oc get envoyfilter -n "$GATEWAY_NAMESPACE"
----

[source]
----
NAME                HOSTNAMES                       AGE
mcp-gateway-route   ["mcp.apps.<cluster-domain>"]   18s

NAME                               AGE
mcp-ext-proc-mcp-gateway-gateway   12s
----

=== Check Controller Logs

[source,bash]
----
oc logs -n mcp-gateway deployment/mcp-gateway-controller --tail=20
----

[#rules-changed]
=== "unknown field spec.rules[].name" in the controller logs

On a cluster whose Gateway API CRDs are older than the controller expects, every reconcile logs these lines:

[source]
----
level=INFO msg="unknown field \"spec.rules[0].name\"" controller=mcpgatewayextension ...
level=INFO msg="unknown field \"spec.rules[1].name\"" controller=mcpgatewayextension ...
level=INFO msg="updating gateway httproute" namespace=mcp-gateway reason="rules changed"
----

The controller writes `spec.rules[].name` on the HTTPRoute it manages. The API server silently drops the field if the installed CRD does not have it, the controller reads the object back, sees its own write missing, and rewrites it - `reason="rules changed"` on a loop. You can confirm the field is being stripped:

[source,bash]
----
oc get crd httproutes.gateway.networking.k8s.io \
  -o jsonpath='{.metadata.annotations.gateway\.networking\.k8s\.io/bundle-version}{"\n"}'

oc get httproute mcp-gateway-route -n mcp-gateway \
  -o jsonpath='{range .spec.rules[*]}name=[{.name}]{"\n"}{end}'
----

A `v1.3.0` bundle and empty `name=[]` values mean you have this mismatch. On OpenShift the Gateway API CRDs are managed by the Cluster Ingress Operator, so you cannot simply upgrade them yourself.

It is noisy but *harmless*: the two rules the controller needs (`/mcp` and `/.well-known/oauth-protected-resource`) are written correctly, only the cosmetic rule names are lost. Two details worth knowing before you spend time on it:

* It also produces occasional `Reconciler error ... the object has been modified; please apply your changes to the latest version` lines, from the controller racing its own rewrite. Same cause, same (lack of) impact.
* It is *not* a permanent hot loop. It burns through rewrites while anything is changing - during install this guide saw 64 - then goes quiet once the configuration settles. Confirm steady state by watching the HTTPRoute stop changing rather than by reading the log:
+
[source,bash]
----
for i in 1 2 3; do
  oc get httproute mcp-gateway-route -n mcp-gateway -o jsonpath='{.metadata.resourceVersion}{"\n"}'
  sleep 30
done
----
+
A `resourceVersion` that stops moving means the controller has settled. Upstream `main` already detects the missing field and skips writing it, so this disappears in a later operator build.

== Custom HTTPRoute

If you need custom HTTP headers (such as CORS headers), you can disable automatic HTTPRoute management and create your own. Set `httpRouteManagement: Disabled` in the MCPGatewayExtension and create a custom HTTPRoute with `ResponseHeaderModifier` filters.

See the link:https://docs.redhat.com/en/documentation/red_hat_connectivity_link/1.4/html/install_the_mcp_gateway/mcp-gateway-install#creating-a-custom-httproute-for-the-mcp-gateway_mcp-gateway-install[Custom HTTPRoute documentation] for details.
