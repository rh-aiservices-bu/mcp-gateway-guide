= Phase 6: Configure {rhbk}

Deploy the {rhbk} ({rhbk}) as the OAuth 2.1 authorization server for {mcp-gw} authentication and authorization.

TIP: All file paths and `oc apply` commands in this guide are relative to the link:{repo-url}[mcp-gateway-guide] repository root.

IMPORTANT: This guide is not a replacement for the link:https://docs.redhat.com/en/documentation/red_hat_connectivity_link/1.4/html/install_the_mcp_gateway/mcp-gateway-install[official {rhcl} {mcp-gw} documentation].

== Overview

This phase deploys a dedicated {rhbk} instance in the `mcp-test` namespace using the RHBK operator, then imports the MCP realm via a `KeycloakRealmImport` CR. The realm configuration includes:

* *MCP realm* - Dedicated realm for MCP Gateway authentication
* *Public client* (`mcp-gateway`) - For CLI and browser-based OAuth flows with PKCE
* *Resource server clients* - One per MCPServerRegistration (`mcp-test/test-server1`, `mcp-test/risk-server`), modeling tool-level roles with a `tool:` prefix
* *Custom client scopes* - `groups` (group membership mapper) and `roles` (client role mapper using `resource_access.$\{client_id\}.roles` claim)
* *Test users* - `mcp/mcp` (full access) and `restricted/restricted` (limited tool access)
* *Groups* - `accounting`, `engineering`, `mcp-users` for group-based authorization

=== User Access Matrix

[cols="1,2,2", options="header"]
|===
| User | Tool Access | Groups

| `mcp` (password: `mcp`)
| All test1_ tools (greet, headers, add_tool, slow, time), all risk_ tools
| accounting, engineering, mcp-users

| `restricted` (password: `restricted`)
| test1_greet only
| mcp-users
|===

=== Role Naming Convention

Tool-level roles use the `tool:` prefix format (e.g., `tool:greet`, `tool:calculate_dti`). This matches the upstream MCP Gateway authorization convention where the authorization CEL expression prepends `tool:` to the tool name from the `x-mcp-toolname` header.

== Prerequisites

* The `mcp-test` namespace must exist (created in Phase 4 when deploying MCP servers)

== Installation

=== Step 1: Install the RHBK Operator

Install the {rhbk} operator in the `mcp-test` namespace with OwnNamespace mode:

[source,bash]
----
oc apply -k manifests/06-deploy-keycloak/operator/
----

Wait for the RHBK operator CSV to succeed:

[source,bash]
----
oc wait csv -n mcp-test \
  -l operators.coreos.com/rhbk-operator.mcp-test="" \
  --for=jsonpath='{.status.phase}'=Succeeded --timeout=600s
----

TIP: The RHBK operator CSV can take 2-3 minutes to appear. If `oc wait` returns "no matching resources found", wait and retry.

=== Step 2: Deploy RHBK with Realm Import

Apply the kustomization which deploys PostgreSQL, the Keycloak CR, and the `KeycloakRealmImport` CR in the `mcp-test` namespace:

[source,bash]
----
oc apply -k manifests/06-deploy-keycloak/keycloak/
----

This creates:

* A PostgreSQL database (`keycloak-pgsql`) for Keycloak storage
* A `Keycloak` CR that the RHBK operator reconciles into a running instance
* A `KeycloakRealmImport` CR that imports the `mcp` realm with users, clients, and roles

=== Step 3: Wait for PostgreSQL

[source,bash]
----
oc wait pod -n mcp-test -l app=keycloak-pgsql \
  --for=condition=Ready --timeout=120s
----

=== Step 4: Wait for Keycloak to be Ready

[source,bash]
----
oc wait keycloak/keycloak -n mcp-test \
  --for=condition=Ready --timeout=300s
----

The RHBK operator provisions a StatefulSet, Services, and a Route for the Keycloak instance. This may take a few minutes on the first deployment.

=== Step 5: Verify the Realm Import

[source,bash]
----
oc get keycloakrealmimport -n mcp-test
----

The import should show as completed. If the import has errors, check the RHBK operator logs:

[source,bash]
----
oc logs deployment/rhbk-operator -n mcp-test --tail=30
----

NOTE: If you need to re-import the realm (e.g., after role changes), you must delete the existing realm first via the Keycloak admin API: `curl -sk -X DELETE -H "Authorization: Bearer $ADMIN_TOKEN" "$\{KEYCLOAK_URL\}/admin/realms/mcp"`, then delete and re-apply the `KeycloakRealmImport` CR.

== Verification

=== Get the Keycloak URL

[source,bash]
----
export KEYCLOAK_URL="https://$(oc get route keycloak -n mcp-test -o jsonpath='{.spec.host}')"
echo "Keycloak URL: $KEYCLOAK_URL"
----

=== Verify OIDC Discovery

[source,bash]
----
curl -sk "${KEYCLOAK_URL}/realms/mcp/.well-known/openid-configuration" | jq '.issuer, .authorization_endpoint, .token_endpoint'
----

You should see the MCP realm endpoints.

=== Access Keycloak Admin Console

Open the Keycloak admin console in your browser:

[source,bash]
----
echo "Admin console: ${KEYCLOAK_URL}/admin"
----

The admin credentials are stored in the `keycloak-initial-admin` secret:

[source,bash]
----
oc get secret keycloak-initial-admin -n mcp-test -o jsonpath='{.data.username}' | base64 -d && echo
oc get secret keycloak-initial-admin -n mcp-test -o jsonpath='{.data.password}' | base64 -d && echo
----

Navigate to the `mcp` realm to verify:

* Clients: `mcp-gateway`, `mcp-test/test-server1`, `mcp-test/risk-server`
* Users: `mcp`, `restricted`
* Groups: `accounting`, `engineering`, `mcp-users`
* Client scopes: `groups`, `roles`

=== Test User Token

Get a token for the `mcp` user to verify the realm is working:

[source,bash]
----
curl -sk -X POST "${KEYCLOAK_URL}/realms/mcp/protocol/openid-connect/token" \
  -H "Content-Type: application/x-www-form-urlencoded" \
  -d "grant_type=password" \
  -d "client_id=mcp-gateway" \
  -d "username=mcp" \
  -d "password=mcp" \
  -d "scope=openid groups roles" | jq '.access_token' -r | cut -d'.' -f2 | base64 -d 2>/dev/null | jq '.resource_access, .groups'
----

You should see the `resource_access` claim with `tool:` prefixed roles per MCP server and the user's groups:

[source,json]
----
{
  "mcp-test/test-server1": {
    "roles": ["tool:greet", "tool:headers", "tool:time", "tool:slow", "tool:add_tool"]
  },
  "mcp-test/risk-server": {
    "roles": [
      "tool:calculate_dti",
      "tool:calculate_ltv",
      "tool:evaluate_credit_risk",
      "tool:assess_income_stability",
      "tool:assess_asset_sufficiency",
      "tool:generate_risk_recommendation"
    ]
  }
}
----

NOTE: The token scope should be `openid groups roles`. Do not include `profile` or `email` scopes unless they are explicitly defined as custom client scopes in the realm - the default built-in scopes may not exist when using the KeycloakRealmImport approach.

=== clientScopeMappings

The realm includes `clientScopeMappings` that allow the `mcp-gateway` public client to receive tool roles from the resource server clients (`mcp-test/test-server1`, `mcp-test/risk-server`) in its access tokens. Without these mappings, the `resource_access` claim in the token would not contain the tool roles.
