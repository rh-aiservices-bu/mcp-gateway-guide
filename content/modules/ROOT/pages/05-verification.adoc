= Phase 5: Verification

Verify end-to-end MCP session initialization and tool discovery through the {mcp-gw}.

== Overview

The MCP protocol uses a JSON-RPC session-based flow. To verify the gateway is working:

1. *Initialize* an MCP session and capture the session ID from response headers
2. *List tools* using the session ID to discover all aggregated tools
3. *Call a tool* to verify end-to-end connectivity

[IMPORTANT]
====
All three steps are required. Stopping after `initialize`, or after `oc get mcpsr -A` shows `Ready`, is the single most common way to sign off a broken install.

Each check covers a different part of the path, and only the last one crosses the Gateway twice:

[cols="1,3", options="header"]
|===
| Check | What it actually proves

| `oc get mcpsr -A` is `Ready` with a `TOOLS` count
| The *controller* reached the backend and read its tool list. Says nothing about the data path.

| `initialize` returns server capabilities
| The Route, the Gateway listener and the broker are reachable. The request never leaves the broker.

| `tools/list` returns prefixed tools
| The broker has an aggregated list cached. Still served from the broker.

| `tools/call` returns a result
| *The only check that exercises the full path*: router rewrites `:authority`, Envoy re-routes on the `mcps` listener, the backend answers.
|===

A wrong `privateHost` or listeners split across two ports passes the first three and fails only the fourth - see xref:03-mcp-gateway-extension.adoc#privatehost[privateHost] and xref:02-gateway-setup.adoc[the same-port requirement].
====

== Verification Steps

=== Step 1: Get the MCP Gateway Endpoint

[source,bash]
----
export MCP_HOSTNAME="mcp.$(oc get ingresses.config.openshift.io cluster -o jsonpath='{.spec.domain}')"
export MCP_URL="https://${MCP_HOSTNAME}/mcp"
echo "MCP endpoint: $MCP_URL"
----

=== Step 2: Initialize MCP Session

Send an `initialize` request and capture the session ID from response headers:

[source,bash]
----
curl -sk -D /tmp/mcp_headers -X POST "${MCP_URL}" \
  -H "Content-Type: application/json" \
  -H "Accept: application/json, text/event-stream" \
  -d '{
    "jsonrpc": "2.0",
    "id": 1,
    "method": "initialize",
    "params": {
      "protocolVersion": "2025-06-18",
      "capabilities": {},
      "clientInfo": {
        "name": "test-client",
        "version": "1.0.0"
      }
    }
  }'
----

You should see a JSON response with the server capabilities:

[source,json]
----
{
  "jsonrpc": "2.0",
  "id": 1,
  "result": {
    "protocolVersion": "2025-06-18",
    "capabilities": {
      "tools": { "listChanged": true }
    },
    "serverInfo": {
      "name": "Kuadrant MCP Gateway",
      "version": "0.0.1"
    }
  }
}
----

=== Step 3: Capture Session ID

Extract the MCP session ID from the response headers:

[source,bash]
----
SESSION_ID=$(grep -i "mcp-session-id:" /tmp/mcp_headers | cut -d' ' -f2 | tr -d '\r')
echo "MCP Session ID: $SESSION_ID"
----

=== Step 4: List Available Tools

Use the session ID to list all tools aggregated by the gateway:

[source,bash]
----
curl -sk -X POST "${MCP_URL}" \
  -H "Content-Type: application/json" \
  -H "Accept: application/json, text/event-stream" \
  -H "mcp-session-id: ${SESSION_ID}" \
  -d '{"jsonrpc": "2.0", "id": 2, "method": "tools/list"}' | jq '.result.tools[].name'
----

You should see prefixed tools from every registered server, plus the gateway's own meta-tools:

[source]
----
"discover_tools"                      <-- gateway meta-tool
"select_tools"                        <-- gateway meta-tool
"dw_ask_wiki_question"                <-- external server, dw_ prefix
"dw_read_wiki_contents"
"dw_read_wiki_structure"
"risk_assess_asset_sufficiency"       <-- risk server, risk_ prefix
"risk_assess_income_stability"
"risk_calculate_dti"
"risk_calculate_ltv"
"risk_evaluate_credit_risk"
"risk_generate_risk_recommendation"
"test1_add_tool"                      <-- test server, test1_ prefix
"test1_greet"
"test1_headers"
"test1_slow"
"test1_time"
...
----

Do not treat the total as fixed - the upstream test image gains tools over time, and your own registrations change it. The check that matters is that every prefix you registered is represented. Count them per prefix:

[source,bash]
----
curl -sk -X POST "${MCP_URL}" \
  -H "Content-Type: application/json" \
  -H "Accept: application/json, text/event-stream" \
  -H "mcp-session-id: ${SESSION_ID}" \
  -d '{"jsonrpc": "2.0", "id": 2, "method": "tools/list"}' \
  | jq -r '.result.tools[].name | split("_")[0]' | sort | uniq -c
----

=== Step 5: Test a Tool Call

Call the risk server's DTI calculation tool with sample mortgage data:

[source,bash]
----
curl -sk -X POST "${MCP_URL}" \
  -H "Content-Type: application/json" \
  -H "Accept: application/json, text/event-stream" \
  -H "mcp-session-id: ${SESSION_ID}" \
  -d '{
    "jsonrpc": "2.0",
    "id": 3,
    "method": "tools/call",
    "params": {
      "name": "risk_calculate_dti",
      "arguments": {
        "monthly_income": 8000,
        "monthly_debts": 2400
      }
    }
  }' | grep '^data: ' | sed 's/^data: //' | jq '.'
----

NOTE: The `tools/call` response uses Server-Sent Events (SSE) format with `content-type: text/event-stream`. The JSON payload is in the `data:` field, so you need to extract it with `grep '^data: '` before piping to `jq`.

Expected response with DTI calculation:

[source,json]
----
{
  "jsonrpc": "2.0",
  "id": 3,
  "result": {
    "content": [
      {
        "type": "text",
        "text": "{\"value\": 30.0, \"rating\": \"Low\", \"guidance\": \"Well within conventional guidelines\"}"
      }
    ]
  }
}
----

=== Step 6: Clean Up Headers File

[source,bash]
----
rm -f /tmp/mcp_headers
----

== Using the Verify Script

You can run all verification steps automatically:

[source,bash]
----
./scripts/verify.sh
----

The script performs the full MCP session flow and validates tool discovery.

== Using MCP Inspector (Optional)

If you have Node.js installed, you can use the official MCP Inspector for interactive testing:

[source,bash]
----
npx @modelcontextprotocol/inspector@latest
----

Then connect to `https://\{MCP_HOSTNAME}/mcp` using the Streamable HTTP transport.

== Troubleshooting

=== No Tools Returned

* Check that MCPServerRegistrations are Ready: `oc get mcpsr -A`
* If a registration is `Ready` but its tools are missing, restart the broker - it loads servers from its config secret at startup: `oc rollout restart deployment/mcp-gateway -n mcp-gateway`
* Check broker logs: `oc logs -n mcp-gateway deployment/mcp-gateway --tail=30`
* Verify the MCP servers are running: `oc get pods -n mcp-test`

=== 503 Instead of a JSON-RPC Response

The Route was admitted but its backend Service does not exist. `oc get route` looks perfectly healthy in this state. Compare the Route's target with the real gateway Service name:

[source,bash]
----
oc get route mcp-gateway -n "$GATEWAY_NAMESPACE" -o jsonpath='{.spec.to.name}{"\n"}'
oc get svc -n "$GATEWAY_NAMESPACE" -l gateway.networking.k8s.io/gateway-name=mcp-gateway -o name
----

The Service is `<gateway-name>-<gatewayclass-name>`, so it is only `mcp-gateway-istio` on the `istio` GatewayClass.

=== 404 Instead of a JSON-RPC Response

The Route reached Envoy but Envoy had no matching route. Usually the `MCPGatewayExtension` is missing or not Ready, so no HTTPRoute was created for the broker: `oc get mcpgatewayextension -n mcp-gateway` and `oc get httproute -n mcp-gateway`.

=== tools/call Fails With "no such host"

`initialize` and `tools/list` work, `tools/call` returns:

[source]
----
failed to create session for mcp server: ... Post
"http://mcp-gateway-istio.mcp-gateway.svc.cluster.local:8080/mcp": ... no such host
----

The broker is dialling a gateway Service that does not exist. This is the `privateHost` default, which assumes the `istio` GatewayClass naming. Compare the two:

[source,bash]
----
oc get mcpgatewayextension mcp-extension -n mcp-gateway -o jsonpath='{.spec.privateHost}{"\n"}'
oc get svc -n "$GATEWAY_NAMESPACE" -l gateway.networking.k8s.io/gateway-name=mcp-gateway -o name
----

Fix it as described in xref:03-mcp-gateway-extension.adoc#privatehost[Setting privateHost], then restart the broker.

=== tools/call Fails But the Host Resolves

If `privateHost` is correct and `tools/call` still fails, check that the public listener and the `*.mcp.local` listener share one port. The `ext_proc` filter is attached to a single port, so a split layout breaks `tools/call` only:

[source,bash]
----
oc get gateway mcp-gateway -n "$GATEWAY_NAMESPACE" \
  -o jsonpath='{range .spec.listeners[*]}{.name}{"\t"}{.port}{"\n"}{end}'

oc get envoyfilter -n "$GATEWAY_NAMESPACE" -o jsonpath='{range .items[*]}{.metadata.name}{"\t"}{.spec.configPatches[*].match.listener.portNumber}{"\n"}{end}'
----

Both listener ports must equal the EnvoyFilter's `portNumber`. See xref:02-gateway-setup.adoc[Phase 2] for why.

=== Connection Refused

* Verify the Gateway is Programmed: `oc get gateway -n mcp-gateway`
* Check the Route exists: `oc get routes -n mcp-gateway`
* Verify DNS resolves: `nslookup \{MCP_HOSTNAME}`

=== Session ID Not Found

* Make sure you are using `-D` flag to dump headers
* Check the response for errors in the initialize call
