= Phase 1: Install the Operators

Install a Gateway API provider and the {mcp-gw} operator via OLM on {ocp-short}.

== Overview

The {mcp-gw} is delivered as an operator through the Red Hat Operator catalog. It is useful to understand up front that the pieces sit in *two layers*, not one flat list - this is the single most common source of confusion when verifying an install.

=== Layer 1: Control plane (installed in this phase)

These are cluster-level components. They exist as soon as the operator is installed, and there is one set of them per cluster.

[cols="1,1,3", options="header"]
|===
| Component | Namespace | Purpose

| MCP Gateway Operator
| `mcp-gateway`
| Installs the CRDs (`MCPGatewayExtension`, `MCPServerRegistration`, `MCPVirtualServer`) and manages the controller

| MCP Gateway Controller
| `mcp-gateway`
| Reconciles those CRDs: creates the broker Deployment, writes its config secret, and manages HTTPRoutes and the Envoy `ext_proc` EnvoyFilter

| {rhcl} dependency operators
| `mcp-gateway`
| Installed automatically as dependencies: Kuadrant, Authorino, Limitador and DNS operators. Needed later for xref:07-authentication.adoc[authentication] and xref:08-authorization.adoc[authorization]
|===

=== Layer 2: Data plane (created in Phase 3)

IMPORTANT: There is *no broker after this phase*. The broker is created by the controller only once an `MCPGatewayExtension` exists, and it is deployed into the *extension's* namespace. You will see it appear in xref:03-mcp-gateway-extension.adoc[Phase 3].

[cols="1,1,3", options="header"]
|===
| Component | Namespace | Purpose

| MCP Broker + MCP Router
| namespace of the `MCPGatewayExtension`
| One pod per extension. Terminates MCP sessions, aggregates tools, and routes `tools/call` requests

| Gateway proxy (Envoy)
| depends on GatewayClass
| The actual data path. With the `istio` GatewayClass it is deployed next to the Gateway object; with an Ingress-Operator-managed GatewayClass it lives in `openshift-ingress`
|===

NOTE: The broker and the router are *not two components*. They are one binary in one container, listening on two ports: `8080` serves the MCP protocol (broker) and `50051` serves gRPC for the Envoy `ext_proc` filter (router). A third port, `8181`, serves its config. Treating them as separate deployments will send you looking for a pod that does not exist.

== Installation

=== Step 1: Choose a Gateway API provider

The {mcp-gw} needs a Gateway API implementation. Before installing anything, find out what your cluster already has:

[source,bash]
----
oc get gatewayclass
----

Pick the track that matches the output:

[cols="1,2,2", options="header"]
|===
| Output | Track | What to do

| No resources found
| *Track A - self-managed OSSM3*
| Continue with Step 2 below. This is the path the rest of the guide follows.

| A GatewayClass already exists (for example `openshift-default`, or a {ocp-short} AI / data-science gateway class)
| *Track B - existing provider*
| *Skip Step 2.* Do not install OSSM3 and do not create an `Istio` CR.
|===

WARNING: On Track B, installing OSSM3 and creating a second `Istio` control plane will *conflict* with the Istio managed by the Ingress Operator in `openshift-ingress`. Only one Istio control plane can own the Gateway API resources.

If you are on Track B, record your values now - later phases need them:

[source,bash]
----
# Name of the GatewayClass you intend to use
export GATEWAY_CLASS="openshift-default"

# Namespace where the Gateway object will live. Your own Gateway does not have
# to sit next to the provider's existing one - a Gateway in mcp-gateway is
# accepted and programmed by an Ingress-Operator-managed GatewayClass too, and
# the proxy is then created in mcp-gateway. Keeping it here is simpler.
export GATEWAY_NAMESPACE="mcp-gateway"
----

On Track A, use the defaults:

[source,bash]
----
export GATEWAY_CLASS="istio"
export GATEWAY_NAMESPACE="mcp-gateway"
----

Track B also changes three things later on, so it is worth flagging them here:

* The Gateway and the `MCPGatewayExtension` end up in *different namespaces*, which makes the xref:03-mcp-gateway-extension.adoc[ReferenceGrant] mandatory rather than optional.
* The extension's default `privateHost` assumes the `istio` GatewayClass naming and will point at a Service that does not exist. You must set it explicitly.
* The gateway proxy Deployment you restart in xref:07-authentication.adoc[Phase 7] is named `<gateway-name>-<gatewayclass-name>`, not `<gateway-name>-istio`. It is created in the *Gateway's* namespace, so it follows `GATEWAY_NAMESPACE` rather than always living in `openshift-ingress`.

=== Step 2: Install OpenShift Service Mesh 3

NOTE: Track A only. If your cluster already has a GatewayClass (Track B), skip this step and go straight to Step 3.

The `istio` GatewayClass is provided by OpenShift Service Mesh 3 (OSSM3). Install the OSSM3 operator:

[source,bash]
----
oc apply -k manifests/01-prerequisites/service-mesh/
----

Wait for the OSSM3 operator to be ready:

[source,bash]
----
oc wait csv -n openshift-operators \
  -l operators.coreos.com/servicemeshoperator3.openshift-operators="" \
  --for=jsonpath='{.status.phase}'=Succeeded --timeout=600s
----

Create the Istio and IstioCNI control plane resources:

[source,bash]
----
oc apply -f manifests/01-prerequisites/service-mesh/istio.yaml
----

Wait for Istio to become ready. The Istio control plane takes 2-3 minutes, and the `Istio` CR does not exist for the first few seconds, so poll instead of a bare `oc wait`:

[source,bash]
----
until oc get istio/default -o jsonpath='{.status.conditions[?(@.type=="Ready")].status}' 2>/dev/null | grep -q True; do
  sleep 10; echo -n "."
done; echo " Istio ready"
----

=== Step 3: Create the Namespace

[source,bash]
----
oc apply -f manifests/01-prerequisites/operators/namespace.yaml
----

=== Step 4: Install the MCP Gateway Operator

NOTE: On {rhcl} 1.5 the {mcp-gw} is bundled in the `rhcl-operator` and there is no `mcp-gateway` subscription. Skip this step and follow xref:rhcl-15.adoc#_phase_1_install_rhcl_1_5_instead_of_the_mcp_gateway_operator[the 1.5 install] instead.

[source,bash]
----
oc apply -k manifests/01-prerequisites/operators/
----

This creates the OperatorGroup and Subscription for the `mcp-gateway` operator from the `redhat-operators` catalog source.

=== Installing into openshift-operators instead

This guide uses a dedicated `mcp-gateway` namespace. Installing the Subscription into `openshift-operators` (AllNamespaces) also works, and the operator supports it:

[source,bash]
----
oc get packagemanifest mcp-gateway -n openshift-marketplace \
  -o jsonpath='{range .status.channels[0].currentCSVDesc.installModes[*]}{.type}={.supported}{"\n"}{end}'
----

[source]
----
OwnNamespace=true
SingleNamespace=true
MultiNamespace=false
AllNamespaces=true
----

Two things change, and both are easy to get wrong:

* *The controller runs in the Subscription's namespace*, so it is in `openshift-operators`, not `mcp-gateway`. Every `oc logs deployment/mcp-gateway-controller -n mcp-gateway` in this guide has to target that namespace instead. Find it without guessing:
+
[source,bash]
----
oc get deploy -A | grep mcp-gateway-controller
----

* *The `MCPGatewayExtension` namespace is still your choice.* It is unrelated to where the operator is installed - the controller watches all namespaces either way, and the broker is created in the *extension's* namespace. Put the extension where you want the broker.

== Verification

=== Wait for the Operator CSV to Succeed

A CSV takes 30-60 seconds to even appear after a Subscription is applied, so `oc wait` reliably fails with `no matching resources found` on the first try. Poll instead:

[source,bash]
----
until oc get csv -n mcp-gateway -l operators.coreos.com/mcp-gateway.mcp-gateway="" \
        -o jsonpath='{.items[0].status.phase}' 2>/dev/null | grep -q Succeeded; do
  sleep 10; echo -n "."
done; echo " MCP Gateway operator installed"
----

The label selector matters. A plain `oc get csv -n mcp-gateway` also lists every operator installed cluster-wide from `openshift-operators`, because OLM copies their CSVs into all namespaces:

[source,bash]
----
oc get csv -n mcp-gateway -o custom-columns='NAME:.metadata.name,PHASE:.status.phase,REASON:.status.reason'
----

[source]
----
NAME                                      PHASE        REASON
limitador-operator.v1.4.2                 Succeeded    InstallSucceeded
mcp-gateway.v0.7.1                        Succeeded    InstallSucceeded
openshift-gitops-operator.v1.22.3         Succeeded    Copied       <-- not yours
rhods-operator.3.5.2                      Succeeded    Copied       <-- not yours
----

Rows with `REASON: Copied` are unrelated operators and can be ignored. Only rows with `InstallSucceeded` were installed by this phase.

=== Verify CRDs Are Available

[source,bash]
----
oc get crd mcpgatewayextensions.mcp.kuadrant.io
oc get crd mcpserverregistrations.mcp.kuadrant.io
oc get crd mcpvirtualservers.mcp.kuadrant.io
----

=== Check the Operator Pods

[source,bash]
----
oc get pods -n mcp-gateway
----

You should see the controller plus the {rhcl} dependency operators:

[source]
----
NAME                                                     READY   STATUS
authorino-operator-7bdd7f85d4-bc29b                      1/1     Running
dns-operator-controller-manager-7c5557d999-m2jdc         1/1     Running
kuadrant-console-plugin-5fbbb5cc98-zg4p4                 1/1     Running
kuadrant-operator-controller-manager-5c56d46647-zfr74    1/1     Running
limitador-operator-controller-manager-56675d65bd-pw924   1/1     Running
mcp-gateway-controller-76ccdf845d-d6p8j                  1/1     Running
----

IMPORTANT: There is deliberately *no broker pod* here. If you are looking for one, see the two-layer explanation in the Overview - the controller creates the broker only after you create an `MCPGatewayExtension` in xref:03-mcp-gateway-extension.adoc[Phase 3].

=== Quick Status Check

[source,bash]
----
oc get subscriptions.operators.coreos.com -n mcp-gateway \
  -o custom-columns='NAME:.metadata.name,CSV:.status.currentCSV,STATE:.status.state'
----

=== Verify the GatewayClass is Accepted

[source,bash]
----
oc get gatewayclass
----

On Track A you should now see the `istio` GatewayClass with `ACCEPTED: True`:

[source]
----
NAME           CONTROLLER                    ACCEPTED   AGE
istio          istio.io/gateway-controller   True       41s
istio-remote   istio.io/unmanaged-gateway    True       41s
----
