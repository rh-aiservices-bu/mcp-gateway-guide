= Phase 8: Authorization

Configure tool-level authorization for the {mcp-gw} using CEL expressions and JWT `resource_access` claims.

== Overview

After configuring authentication (Phase 7), you can add fine-grained tool-level authorization. The {mcp-gw} broker injects `x-mcp-toolname` and `x-mcp-servername` headers when forwarding requests to backend MCP servers via the internal `mcps` listener. An AuthPolicy on that listener evaluates CEL expressions against JWT claims to enforce access control.

=== Two-AuthPolicy Architecture

Authorization requires two AuthPolicy resources targeting different Gateway listeners:

[cols="1,1,2", options="header"]
|===
| AuthPolicy | Listener | Purpose

| `mcp-auth-policy` (Phase 7)
| `mcp` (public)
| JWT validation for all incoming requests

| `mcp-authz-policy` (this phase)
| `mcps` (internal)
| Tool-level authorization based on roles
|===

This separation is necessary because of how the request flows through the system:

1. Client sends a request to the public `mcp` listener
2. `mcp-auth-policy` validates the JWT on the `mcp` listener
3. The broker processes the request and identifies the target tool
4. The broker forwards the request to the internal `mcps` listener with `x-mcp-toolname` and `x-mcp-servername` headers
5. `mcp-authz-policy` checks the tool headers against the user's roles on the `mcps` listener

IMPORTANT: Do NOT delete the `mcp-auth-policy` from Phase 7. Both policies must coexist. The auth policy handles JWT validation on the public listener, while the authz policy handles tool access on the internal listener.

=== How It Works

1. User authenticates and receives a JWT with `resource_access` claims
2. The JWT contains tool roles per MCP server using a `tool:` prefix
3. When a `tools/call` request arrives, the broker forwards it to the internal listener with `x-mcp-toolname` and `x-mcp-servername` headers
4. The authorization AuthPolicy on the `mcps` listener evaluates: "does the user have a `tool:<toolname>` role for this server?"

=== resource_access Claim Structure

[source,json]
----
{
  "resource_access": {
    "mcp-test/test-server1": {
      "roles": ["tool:greet", "tool:headers", "tool:add_tool", "tool:slow", "tool:time"]
    },
    "mcp-test/risk-server": {
      "roles": ["tool:calculate_dti", "tool:calculate_ltv", "tool:evaluate_credit_risk", "..."]
    }
  }
}
----

Roles use the `tool:` prefix format. The CEL expression prepends `tool:` to the tool name from the `x-mcp-toolname` header before matching.

The `mcp` user has access to all tools on both servers. The `restricted` user only has `tool:greet` on the test server.

=== When Authorization is Skipped

The authorization `when` conditions ensure the policy only evaluates during actual tool execution:

* `x-mcp-toolname` header must be present (set by the broker for tool-related requests)
* `x-mcp-method` header must equal `tools/call` (distinguishes tool execution from session setup)

The broker sets `x-mcp-toolname` on all requests to backend servers, including during session creation (`initialize`, `notifications/initialized`). Without the `x-mcp-method` filter, the authorization would deny session setup requests, causing the broker to return a misleading `500 Internal Server Error` instead of a clean `403 Forbidden`.

== Installation

TIP: For a detailed explanation of the AuthPolicy, the CEL expression, and the two-policy architecture, see the link:{repo-url}/tree/main/manifests/08-authorization[manifests/08-authorization README].

=== Step 1: Apply the Authorization Policy

[source,bash]
----
export KEYCLOAK_URL="https://$(oc get route keycloak -n mcp-test -o jsonpath='{.spec.host}')"
export KEYCLOAK_ISSUER="${KEYCLOAK_URL}/realms/mcp"

envsubst < manifests/08-authorization/authpolicy-authz.yaml.tmpl | oc apply -f -
----

Wait for the AuthPolicy to be enforced:

[source,bash]
----
oc wait authpolicy/mcp-authz-policy -n mcp-gateway \
  --for=condition=Enforced --timeout=60s
----

=== Step 2: Verify Both Policies Exist

`oc get authpolicy` has no status column, so ask for the condition explicitly:

[source,bash]
----
oc get authpolicy -n mcp-gateway \
  -o custom-columns='NAME:.metadata.name,ENFORCED:.status.conditions[?(@.type=="Enforced")].status'
----

[source]
----
NAME               ENFORCED
mcp-auth-policy    True
mcp-authz-policy   True
----

Both must be `True`. A plain `oc get authpolicy -n mcp-gateway` only prints `NAME` and `AGE`, which tells you nothing about enforcement.

=== Key CEL Expression

The authorization rule uses this CEL predicate:

[source]
----
('tool:' + request.headers['x-mcp-toolname']) in (
  has(auth.identity.resource_access) &&
  auth.identity.resource_access.exists(p, p == request.headers['x-mcp-servername'])
    ? auth.identity.resource_access[request.headers['x-mcp-servername']].roles
    : []
)
----

This checks:

1. Prepend `tool:` to the tool name from the `x-mcp-toolname` header
2. Does `resource_access` exist in the JWT?
3. Does it contain an entry for the requested server (`x-mcp-servername`)?
4. Does the user have a role matching `tool:<toolname>` for that server?

== Verification

=== Test with Full-Access User

Get a token for the `mcp` user and call a risk tool:

[source,bash]
----
export MCP_HOSTNAME="mcp.$(oc get ingresses.config.openshift.io cluster -o jsonpath='{.spec.domain}')"

TOKEN=$(curl -sk -X POST "${KEYCLOAK_ISSUER}/protocol/openid-connect/token" \
  -H "Content-Type: application/x-www-form-urlencoded" \
  -d "grant_type=password&client_id=mcp-gateway&username=mcp&password=mcp&scope=openid groups roles" | jq -r '.access_token')

# Initialize session
curl -sk -D /tmp/mcp_headers -X POST "https://${MCP_HOSTNAME}/mcp" \
  -H "Content-Type: application/json" \
  -H "Authorization: Bearer ${TOKEN}" \
  -d '{"jsonrpc":"2.0","id":1,"method":"initialize","params":{"protocolVersion":"2025-06-18","capabilities":{},"clientInfo":{"name":"test","version":"1.0.0"}}}'

SESSION_ID=$(grep -i "mcp-session-id:" /tmp/mcp_headers | cut -d' ' -f2 | tr -d '\r')

# Call risk_calculate_dti - should succeed
curl -sk -X POST "https://${MCP_HOSTNAME}/mcp" \
  -H "Content-Type: application/json" \
  -H "Authorization: Bearer ${TOKEN}" \
  -H "mcp-session-id: ${SESSION_ID}" \
  -d '{"jsonrpc":"2.0","id":2,"method":"tools/call","params":{"name":"risk_calculate_dti","arguments":{"monthly_income":8000,"monthly_debts":2400}}}' \
  | grep '^data: ' | sed 's/^data: //' | jq '.'
----

=== Test with Restricted User

Get a token for the `restricted` user and try the same tool:

[source,bash]
----
RESTRICTED_TOKEN=$(curl -sk -X POST "${KEYCLOAK_ISSUER}/protocol/openid-connect/token" \
  -H "Content-Type: application/x-www-form-urlencoded" \
  -d "grant_type=password&client_id=mcp-gateway&username=restricted&password=restricted&scope=openid groups roles" | jq -r '.access_token')

# Initialize session with restricted token
curl -sk -D /tmp/mcp_headers_r -X POST "https://${MCP_HOSTNAME}/mcp" \
  -H "Content-Type: application/json" \
  -H "Authorization: Bearer ${RESTRICTED_TOKEN}" \
  -d '{"jsonrpc":"2.0","id":1,"method":"initialize","params":{"protocolVersion":"2025-06-18","capabilities":{},"clientInfo":{"name":"test","version":"1.0.0"}}}'

RESTRICTED_SESSION=$(grep -i "mcp-session-id:" /tmp/mcp_headers_r | cut -d' ' -f2 | tr -d '\r')

# Try to call risk_calculate_dti - should be denied (403)
curl -sk -X POST "https://${MCP_HOSTNAME}/mcp" \
  -H "Content-Type: application/json" \
  -H "Authorization: Bearer ${RESTRICTED_TOKEN}" \
  -H "mcp-session-id: ${RESTRICTED_SESSION}" \
  -d '{"jsonrpc":"2.0","id":3,"method":"tools/call","params":{"name":"risk_calculate_dti","arguments":{"monthly_income":8000,"monthly_debts":2400}}}' \
  | grep '^data: ' | sed 's/^data: //' | jq '.'
----

The restricted user should receive a `403 Forbidden` response because they do not have `tool:calculate_dti` role on the risk server.

=== Test Allowed Tool for Restricted User

[source,bash]
----
# Call test1_greet - should succeed for restricted user
curl -sk -X POST "https://${MCP_HOSTNAME}/mcp" \
  -H "Content-Type: application/json" \
  -H "Authorization: Bearer ${RESTRICTED_TOKEN}" \
  -H "mcp-session-id: ${RESTRICTED_SESSION}" \
  -d '{"jsonrpc":"2.0","id":4,"method":"tools/call","params":{"name":"test1_greet","arguments":{}}}' \
  | grep '^data: ' | sed 's/^data: //' | jq '.'
----

This should succeed because the restricted user has `tool:greet` role on `mcp-test/test-server1`.

=== Expected Results Matrix

Authorization applies identically to in-cluster and external servers. Running all four combinations is the quickest way to prove the policy is actually doing something:

[cols="1,1,1,2", options="header"]
|===
| User | Tool | Result | Why

| `mcp`
| `risk_calculate_dti`
| Allowed
| Has `tool:calculate_dti` on `mcp-test/risk-server`

| `restricted`
| `risk_calculate_dti`
| Denied
| No roles on `mcp-test/risk-server`

| `restricted`
| `test1_greet`
| Allowed
| Has `tool:greet` on `mcp-test/test-server1`

| `mcp`
| `dw_read_wiki_structure`
| Allowed
| Has `tool:read_wiki_structure` on `mcp-test/external-server`

| `restricted`
| `dw_read_wiki_structure`
| Denied
| No roles on `mcp-test/external-server`
|===

A denial returns the JSON-RPC error defined in the policy's `response.unauthorized` block:

[source,json]
----
{
  "jsonrpc": "2.0",
  "error": {
    "code": -32600,
    "message": "Forbidden: Insufficient permissions for this tool."
  }
}
----

== Authorizing a Newly Registered Server

Registering an MCP server in xref:04-register-mcp-servers.adoc[Phase 4] does *not* grant anyone access to its tools. Until {rhbk} knows about the server, no token carries roles for it and every `tools/call` is denied. This is the single most common surprise after adding a server.

For each new server you need three things in the realm:

. A *resource-server client* whose `clientId` exactly matches the value the broker puts in the `x-mcp-servername` header - which is `<namespace>/<registration-name>`, for example `mcp-test/external-server`.
. *Client roles* named `tool:<unprefixed-tool-name>`. Note the tool name *without* the registration prefix: the tool exposed as `dw_read_wiki_structure` needs the role `tool:read_wiki_structure`.
. A *clientScopeMapping* granting those roles to the public `mcp-gateway` client, otherwise they never appear in the `resource_access` claim.

The declarative way is to add them to `manifests/06-deploy-keycloak/keycloak/keycloakrealmimport-mcp.yaml`, which is how `mcp-test/external-server` is defined:

[source,yaml]
----
clients:
  - clientId: mcp-test/external-server
    name: External MCP Server Resource
    enabled: true
    bearerOnly: true
    publicClient: false
    protocol: openid-connect
    defaultClientScopes: ["openid"]

users:
  - username: mcp
    clientRoles:
      mcp-test/external-server:
        - tool:read_wiki_structure
        - tool:read_wiki_contents
        - tool:ask_wiki_question

clientScopeMappings:
  mcp-test/external-server:
    - client: mcp-gateway
      roles:
        - tool:read_wiki_structure
        - tool:read_wiki_contents
        - tool:ask_wiki_question
----

IMPORTANT: `KeycloakRealmImport` does not update an existing realm. To pick up changes you must delete the realm and re-import it, as described in xref:06-deploy-keycloak.adoc[Phase 6]. On a live system, add clients and roles through the Keycloak admin console or admin API instead.

Confirm the roles reach the token before testing a tool call:

[source,bash]
----
curl -sk -X POST "${KEYCLOAK_ISSUER}/protocol/openid-connect/token" \
  -H "Content-Type: application/x-www-form-urlencoded" \
  -d "grant_type=password&client_id=mcp-gateway&username=mcp&password=mcp&scope=openid groups roles" \
  | jq -r '.access_token' | cut -d'.' -f2 \
  | python3 -c 'import sys,base64,json; s=sys.stdin.read().strip(); print(json.dumps(json.loads(base64.urlsafe_b64decode(s+"="*(-len(s)%4)))["resource_access"], indent=2))'
----

If the new server is absent from `resource_access`, the `clientScopeMappings` entry is missing or misspelled.

=== Envoy Filter Chain Order

Understanding the filter chain helps debug auth issues:

1. `ext_proc` (INSERT_FIRST) - The MCP Gateway broker
2. WASM/Kuadrant plugin (INSERT_BEFORE router) - Authorino integration
3. Router - Final routing to backends

On the public `mcp` listener, the WASM plugin enforces `mcp-auth-policy` (JWT validation). On the internal `mcps` listener, it enforces `mcp-authz-policy` (tool-level authorization). The broker sits between them, setting the `x-mcp-toolname` and `x-mcp-servername` headers after processing the MCP request.
